# R87: RyukGram settings and default data protection (rest of R86)

## Verdict
- A launch while locked of an app signed with default-data-protection NSFileProtectionComplete does not write over the settings in anything run here. It sees none: the preferences file open fails with EPERM (errno 1), the process reads 46 (or 8) default keys, the marker key is nil, and keychain reads return -25308 (errSecInteractionNotAllowed). The OS then kills the process with SIGBUS "FS pagein error: 1 Operation not permitted". The same crash as the user's 18 Pro reports at 12:05 and 15:36 EST. The process ends from the OS, not because the app judged its preferences unreadable. The preferences file kept its marker and keys through all locked launches.
- Re-signing without Complete (B413's signer) does NOT un-protect existing files. Files created under Complete stay class A (1). Only files rewritten after the re-sign take the new default: the preferences plist went from class 1 to class 3. Folders go to class 0 (no class set). A file the app maps, Library/Application Support/mapped_storage/sessionless/crash_counter (read by FBSharedFramework's crash counter), stayed class 1, so a locked launch of the B413-signed copy still died with the same SIGBUS. After deleting crash_counter and crash_counter_metadata, a locked launch of the same copy survived: preferences readable (class 3, 191 to 197 keys, marker present), keychain -25308 while locked and 0 after unlock. Filed B415 (critical): the group fix lowers the protection of existing files and folders at launch.
- Installing a Complete-signed build over an existing container re-classed the existing files to Complete (class 1) before the app wrote anything. The pre-signed installed copy's preferences plist was class 1 at start, and Library/Caches, Application Support, AppGroups and Preferences were all class 1. So the protection is applied to the folders and files of an installed app at update time, and a later update without the entitlement does not remove it.
- Sign-out: none seen, but the Complete locked processes died within seconds, so this only covers what a process that short could do; password counts were one generic-password query, not split per group. Instagram stayed signed in through every locked launch. The -25308 password read appears in the group fix log, and "copied in" was tried again with "pinned no" in the two Complete locked launches. Password counts were 44 to 46 before and after, and the app was signed in at the end, when RyukGram's settings screen opened. The sign-in also survived an uninstall and a reinstall under another App ID, because the keychain group TEAM.com.burbn.instagram kept the session.
- The user's 23:24Z group fix line is reproduced: "ran before yes, 8 preferences ... saw passwords error -25308 ... isolate ...: copied in generic read -25308; pinned no". In the locked launch of the no-Complete copy the mark was readable: "preferences 196, saw passwords error -25308, isolate marked earlier, pinned yes". So "pinned no" and the repeated copy-in appear only with unreadable preferences (Complete). The -25308 password read is the keychain's own WhenUnlocked class while locked, and it happens with or without Complete. The unpinned group fix run did not delete anything here (no item count dropped, no sign-out). It is still the reason to keep the isolate mark readable while locked, which B415 covers, since a lowered class makes the mark readable.
- SideDrop: it signs with the profile's entitlements verbatim (only application-identifier, keychain-access-groups and get-task-allow are changed). Every app signed with SideDrop's ad hoc profile (RSideload/sidedrop-adhoc, which carries com.apple.developer.default-data-protection NSFileProtectionComplete) therefore gets Complete. Its code has no default-data-protection handling. Reported only; the repo was not changed.
- Settings changed through RyukGram's UI: not done. The RyukGram settings screen was reached on the 15 Pro (signed in, via the tab bar's profile) but nothing was changed through it. The probe watched RyukGram's own key hide_ads_comments (already 1 after a fresh install, which is RyukGram's default) and its own marker key written by the probe (ryprobe.marker).

## Method
- Phone: iPhone 15 Pro, iOS 27, driven with tools/ui-15.sh under the R87 lock. Instagram/RyukGram 456 IPA (the one B390 used: Info.plist file sharing on, the probe loaded as a dependency of CydiaSubstrate, Frameworks/ryspy.dylib). Signed with SideDrop's certificate and ad hoc profile (App ID com.ryha.sideload). The phone's earlier copy had App ID com.ryha.instagram from another profile, so it was uninstalled and the app installed fresh. The keychain kept the sign-in.
- Signed by iFizBox's native signer (native/sign/bench signbench-linux, see sign.sh in this folder). "pre" is the commit before B413, which puts Complete in. "new" is this tree (B413, no Complete). Both carry the group fix dylib. strings confirmed that pre has default-data-protection in its signature and new has none.
- probe.m (this folder): per launch it logs via os_log (read live with pymobiledevice3 syslog) and to Documents/ryprobe.log when writable. Logged: app state, protectedDataAvailable, preference key count, the preferences file class (fcntl F_GETPROTECTIONCLASS 63; 1 = Complete, 3 = until first user authentication, 4 = none) and whether it reads, the marker, the keychain read status. Sampling points: the constructor, +3, +10 (class counts of every container file), +25, +60 and +120 s. If Documents/ryprobe.sleep exists, the constructor deletes it and sleeps 18 s before any app code runs.
- A passcode was needed. The phone had none, so protectedDataAvailable stayed 1 after locking and class A never locked. A throwaway passcode was set in Settings for the test and turned off at the end, so the phone is back to no passcode. Unlocking was done by typing it on the lock screen keypad.
- Locked launch: go-ios `ios launch` and pymobiledevice3 `dvt launch` are denied by SpringBoard while locked ("RequestDenied ... Locked"). `dvt launch --suspended` needs get-task-allow, which the ad hoc profile sets to false. So a real background launch could not be triggered. Stand-in: launch the app while unlocked with the probe's 18 s start delay, then press the lock button 2 s later. The app's own initialisation (everything after the probe's constructor: UIApplicationMain, preferences, keychain) then runs with the phone locked (process state background, protectedDataAvailable 0). One process started while locked, not by my launch, was caught by chance (2026-11-24 02:52Z, after `ios kill`): same result (open errno 1, 46 keys, -25308). That process was created from SpringBoard while unlocked rather than by the system, so its scene state differs from a push or refresh launch.
- Sequence: new install (no Complete) foreground; pre install (Complete) foreground (files re-classed to 1); locked launch of pre (SIGBUS at 0.3 s, or the process vanished after t3), three times; new install (files stay 1, preferences rewritten to 3); locked launch (SIGBUS, same frames); delete the crash_counter files; locked launch (survived, readable); reinstall the plain IPA (no probe, new signer) to leave the phone clean.
- Crash logs: Instagram-2026-11-23-220303.ips (pre, locked, SIGBUS pagein; the thread is in FBSharedFramework, XPluginsGetListLookupDataPair), 220901 (pre) and 221318 (new, before crash_counter was deleted). All show EXC_BAD_ACCESS SIGBUS "FS pagein error: 1 Operation not permitted", with frames FBSharedFramework FBInstacrashCounterGetPostMainCrashCount <- Instagram XPluginsGetFuncPtr <- METARunPreApplicationMain. 220541 was the probe's own sleep hitting the 20 s launch watchdog (28 s sleep); ignore it.

## Filed
- B415 (critical): the group fix lowers the protection of existing files and folders at launch. Re-signing without Complete does not restore class A on files already created under Complete, so a locked launch can still die on the mapped crash_counter file.

## Not verified
- A real system background launch while locked (a push or refresh launch): it could not be triggered. The stand-in is described above, and one process that started while locked by itself matched it (its trigger is not known).
- Whether a locked Complete process that survives long enough writes over the settings. Every locked Complete process died within about 0.3 s to a few seconds (one survived to the 3 s sample) or was killed, and the preferences file and keys were intact afterwards. A long-lived locked process (the user's 23:24Z case) was not reproduced.
- Settings changed through RyukGram's own UI and kept across the test: not done, because the probe-set key and marker were used instead.
- The user's iPhone 18 Pro, its files, and whether its crash_counter is class A: not read, because the phone was not connected. The 15 Pro shows the mechanism; the user's copy follows it only if their files were created under Complete.
- B413's own signer output on the phone (the Swift signer): the Linux build of the same sources was used instead.
- Whether files other than crash_counter (mapped files in Caches or WebKit) would also kill a locked launch: only crash_counter was removed. After removing it, the process survived 60 s locked and then unlocked cleanly.
- iOS 27 only.
